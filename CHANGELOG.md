# Changelog

## 0.1.0: pi-discord-openclaw 首版（Telegram → Discord 迁移）

- `Platform Migration`: pi-telegram-openclaw 就地改造为 pi-discord-openclaw：transport 从 Telegram Bot API（long polling）换成 Discord REST + Gateway，保留 OpenClaw 风格流式（draft/reasoning/progress/debounce lanes）。Impact: 在 Discord 上获得与 Telegram 版一致的 🧠 思考 / 🔧 工具进度 / 📝 流式编辑体验。
- `Discord Transport`: 新增零依赖 transport 层（原生 fetch + WebSocket）——`src/transport/discord-rest.ts`（Bot header、v10 API、429 retry-after 重试、超时）与 `src/transport/discord-gateway.ts`（identify/heartbeat/resume/断线重连、MESSAGE_CREATE 分发）。Impact: 无第三方 SDK 依赖，Node ≥ 22 即可运行。
- `Streaming Adaptation`: 消息分块从 Telegram 4096/3800 调整为 Discord 2000/1900 上限；messageId 从 number 改为 snowflake string；进度行渲染从 HTML 标签改为 Discord Markdown（`**label**` `detail` `*status*`）。Impact: 适配 Discord 2000 字符硬限制与 Markdown 语法。
- `Config`: 配置从 telegram.json 迁移到 discord.json（token/channels/ignoreBots + openclawStyle 段），支持 `DISCORD_BOT_TOKEN` 环境变量。Impact: 按 discord.json 启用 openclawStyle 或跳过。
- `Entrypoint`: index.ts 重写为精简 Discord bridge（Gateway 收消息 → 过滤 → pi.sendUserMessage；pi 事件 → lanes → REST 发送/编辑），删除 Telegram 专属 lib/vendor/api（56+ 模块）与上游测试。Impact: 代码量从 1174 行入口 + 56 lib 模块收敛到 ~230 行入口 + 分层 transport/lanes。
- `Tests`: 12 个用例全绿——transport-rest（发送/编辑/删除/typing/429 重试/错误）、transport-gateway（identify/heartbeat/resume/重连/fatal）、draft/lanes/dispatch/adapter 回归。Impact: typecheck 0 error，npm test 全绿。

## 0.27.0: Telegram Commentary Delivery

- `Telegram Commentary`: Completed intermediate assistant text segments from Telegram-originated turns now arrive once as independent messages on the immutable originating target before the existing final reply. The path remains active independently of local/autonomous Proactive Push, preserves normalized segment order, rendering, authority fencing, and no-replay behavior, and leaves final/terminal settlement with the established active-turn delivery pipeline. Impact: commentary cannot be overtaken by the final result, while Pi lifecycle completion remains non-blocking and stale session/transport generations still fail closed.

## 0.26.16: Follower Edit Normalization Hotfix

- `Follower Edit Normalization`: The bus-routed `editMessageText` path now treats Telegram's "message is not modified" rejection as an unchanged edit instead of a failure, matching the direct transport path. Impact: reasoning activity on follower instances no longer freezes its thinking block when an edit targets identical content (for example a repeated reasoning-end flush), because the failed edit no longer marks the whole block as blocked.

## 0.26.15: Follower Bus Timeout Hotfix

- `Follower Bus Timeout`: Restored the 30-second default for follower-client bus calls (update forwarding, thread-target control, and API calls) after an entrypoint compression pass dropped the explicit timeout and left the forwarding path falling through to the 1-second transport default. The shared default now lives on the follower client runtime as `TELEGRAM_BUS_FOLLOWER_CLIENT_TIMEOUT_MS`. Impact: leader-to-follower update forwarding no longer times out under load, so polling stops re-fetching and re-downloading the same update (which previously delivered one voice message as three identical turns).

## 0.26.14: Reasoning Activity Throttle

- `Reasoning Throttle`: Added a minimum interval between reasoning-block edits (`TELEGRAM_REASONING_MIN_INTERVAL_MS = 1_200`) so the first frame publishes immediately while later frames wait until both the interval and the 160-char delta threshold pass. The final `reasoning-end`/`agent-end` flush stays unconditional, and the 24-frame cap is unchanged. Impact: fast-token models with very large reasoning blocks no longer push an edit per character burst, so parallel threads stop saturating the bus and inbound Telegram messages arrive without multi-second delay.
